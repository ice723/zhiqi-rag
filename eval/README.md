# 检索链路评测说明（面试复习用）

> 2026-10-24 执行。数据：12 本设备手册 / 276 chunks / 12 个主体实体。
> 脚本：`run_eval.py`（双模式检索消融 + 实体对齐），题库：`eval_questions.json`，明细：`eval_results.json`。

## 一、评测设计

**检索消融（16 题：8 单实体直问 + 8 口语化改写，覆盖 11 本手册）**

| 配置 | 链路 |
|---|---|
| C1 基线 | BGE-M3 稠密+稀疏双向量 → Milvus 混合检索 |
| C2 +HyDE | 基线 + HyDE 假设文档检索，两路 RRF(k=60) 融合 |
| C3 +重排 | C2 + Cross-Encoder 精排 + 断崖式截断（分差≥0.5 或 比率≥0.25） |

两个模式：
- **线上链路**：带 item_name 实体过滤（节点 A 确认主体后圈定单手册范围），即真实运行方式
- **全库压力**：去掉实体过滤，276 chunks 跨 12 本手册竞争，命中还要求来自正确手册（4 本华为台式机手册有大量雷同章节：键盘/电池安全/儿童健康，是最难的判别场景）

**实体对齐（节点 A 双阈值三档策略）**：12 个库内标准主体名（期望 top1 归一化分 ≥0.8 自动确认）+ 8 个库外不存在设备名（期望 <0.6 直接拒答；0.6~0.8 为澄清反问区）。检索 kb_item_names 集合，权重 (0.8, 0.2)，norm_score=True。

## 二、结果

| 指标 | 线上链路（实体过滤） | 全库压力（无过滤） |
|---|---|---|
| C1 基线 命中率@5 | 100% | 100% |
| C2 +HyDE/RRF | 100% | 94% |
| C3 +重排（全链路） | **100%** | **81%** |
| 基线检索延迟中位数 | 284ms | 279ms |
| HyDE 增路延迟中位数 | ~11s（LLM 生成主导） | ~11s |
| 重排延迟中位数 | 148ms | 151ms |

实体对齐：库内 12/12 自动确认（top1 最低 0.911）；库外 0 误确认（最高分 0.775 < 0.8 阈值），2/8 直接拒答，6/8 落入澄清区（0.6~0.8）。

## 三、结论（面试话术要点）

1. **线上链路 16 题 100% 命中@5**：端到端架构（实体过滤 → 三路召回 → RRF → 重排）有效，直问和口语改写题均 100%。
2. **实体过滤是最关键模块**（消融证据）：去掉后全链路命中率从 100% 降到 81%——4 本华为手册雷同章节场景下，Cross-Encoder 只看 query-文档相关性、无法判断"该答哪本手册"，此时**元数据过滤比精排更本质**。这验证了"先用结构化信息圈定范围、再用语义精排"的架构决策。
3. **HyDE 是负收益的诚实结论**：本库场景下 +HyDE 在压力模式反而 -6%（假设文档带偏一次召回），且增路成本 ~11s（LLM 生成主导）。线上保留它的理由是三路并行+RRF 对冲单路波动的鲁棒性设计；优化方向：换小模型/限制假设文档长度/仅对改写类 query 启用。
4. **双阈值防线保证了"绝不答错手册"**：库内确认线（0.8）与库外最高分（0.775）之间有安全间隔；库外实体 0 误确认，75% 进入澄清反问而不是胡乱作答——代价是多一轮对话，属于可接受的 UX 取舍。
5. **延迟画像**：基线检索 ~280ms（BGE-M3 本地 GPU 推理 + Milvus 混合检索），重排 ~150ms，均在交互可接受范围；HyDE 是延迟瓶颈（面试可聊：异步预生成/缓存/小模型替换）。

## 四、诚实性备注

- 命中判定为"前 5 条结果中存在包含全部期望关键词、且（压力模式下）来自正确手册的 chunk"，题库与关键词标注见 `eval_questions.json`，可复现。
- 评测绕过节点 A（依赖 MongoDB 历史）与节点 D（联网搜索，无 chunk_id 不参与本地命中率），属合理简化。
- 16 题为小样本，结论方向可信、具体数字有波动空间；面试如实说明规模。
